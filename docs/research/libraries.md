# Visualization libraries: comparison and architectural lessons

Evidence accessed **2026-11-26**. `Rxx`/`Pxx` resolve to exact URLs and revisions in [the source index](source-index.json). The matrix combines documented/source-observed facts with an explicitly labeled **DeepViz role**, which is our recommendation. No upstream performance example is a DeepViz measurement.

## AntV findings that change implementation choices

### G2 v5 and G2Plot are not interchangeable

G2's inspected `src/spec/mark.ts` separates data mappings, scale/coordinate configuration, transforms, components, interactions, theme, and mark style. `src/api/runtime.ts` takes a renderer and defaults to Canvas. That separation fits a compiler from a smaller execution-free DeepViz chart contract. It does **not** justify accepting the entire upstream option surface as untrusted JSON. (R01)

G2Plot's English README explicitly identifies G2 4.x, states no plan for a G2-v5-based G2Plot v3, and points users to other options for newer integrations. Its package file requests G2 `^4.2.12`. This is a concrete compatibility reason to implement the requested `antv` adapter against G2 v5, not a claim that G2Plot is archived or incapable. Repository metadata observed it as non-archived. (R02)

### AVA: distinguish two public implementations

- **Current default `ai` revision:** `adviseChartType` prompts a language model and checks the returned chart type against a known set. The generator asks for a chart-specific JSON configuration, wraps it in HTML, and loads a pinned GPT-Vis script from a remote package mirror. The contracts use a chart-type discriminated union. These are source-observed choices, not a statement about hidden AntV services. (R03, `ai` files)
- **Legacy `v3` revision:** Advisor exposes advice and lint results with logs. The inspected recommendation pipeline performs hard-rule pruning, soft scoring, field mapping, optional design/color refinement, and score ordering. Its input-preparation path clones the input; the optional color path includes random choice. Do not assume bounded memory or deterministic output without controlling those paths. (R03, `v3` files)
- **DeepViz recommendation:** separate hard constraints (field types, chart semantics, supported adapter features) from explainable ranking. Supply bounded profiles and redacted examples; preserve recommendation reasons and deterministic ties. Treat model proposals as candidates that must pass the same validator as human requests.

### A useful recommendation result

Return a shortlist such as `{kind, fields, reasons, rejected_constraints, reduction, estimated_output_rows}`. For example: a time field plus one numeric measure suggests a line; unsorted input requires a sort plan, duplicates require an explicit reducer, and a million source rows require a pixel-aware representation. A numeric pair suggests scatter **or density**, depending on point/pixel ratio. Category cardinality and label length should affect bar orientation and top-k/other decisions. These are design proposals; the present model contract does not yet encode every field in this example.

## Specification design: adopt principles, not every API

1. **Semantic core:** keep chart intent, fields/types, units, grouping, ordering, null policy, domains and aggregation distinct from renderer options. The current `ChartSpec` is deliberately smaller than Vega-Lite, G2 or ECharts. Add expressive features through a versioned contract rather than an unchecked `options` escape hatch. (Design inference from R01, R05, R06.)
2. **One reduction owner:** avoid server `mean` followed by renderer `mean`, or a histogram of already-counted bins. Compile the reduced dataset with explicit bin boundaries/weights and disable equivalent implicit transforms. Test computed values before testing pixels. (DeepViz recommendation.)
3. **Portable semantics, not identical interaction:** a static figure cannot provide a browser crossfilter, and a GL scatter export may not be fully vector. A dashboard layout does not imply linked selections. Reject unsupported requests or return an explicit, accepted fallback; never silently rename a different plot. (R07/P18, R13/P22; design inference.)
4. **Lifecycle:** expose prepare/render/update/dispose internally, record renderer readiness, and free event handlers/canvases/workers. A cached spec and cached data are separate objects with separate privacy lifetimes. (DeepViz recommendation; Vega view API P12 is a useful reference.)

## Themes and accessibility

Use one trusted token set: background/surface/foreground, muted text, grid, accent, sequential/diverging/categorical scales, font family/size, spacing, focus and selection. Translate it to G2 themes, Vega-Lite `config`, Plotly templates and ECharts styles. These upstream mechanisms are documented or source-observed; **perceptual parity is our responsibility**, not an upstream guarantee. (R01, P11, P16, P19)

Validate both light and dark outputs with long labels, many categories, missing values and mixed signs. Reserve sequential color for ordered magnitudes, diverging color for a meaningful midpoint, and categorical palettes for identity; do not encode identity with a sequential ramp. Add a text summary and accessible table/export; canvas images alone are insufficient. Pin font assets for image tests, and separate semantic correctness checks from small antialiasing differences. These are DeepViz acceptance recommendations, not claims that every upstream renderer supplies equivalent accessibility.

## License and adoption boundary

The matrix reports licenses **read at the pinned revisions**, not an attorney's opinion or a complete dependency-license audit. Preserve required notices and inspect dependency/assets/font/map-data terms before distribution. Open-source library code does not imply that a hosted service, commercial extension, sample dataset or map tile provider shares its license. OmO is intentionally outside the visualization-license matrix: its inspected Sustainable Use License has restrictions and must not be represented as MIT/BSD/Apache software. (R01–R15 license files)

## Recommended adoption order

**Baseline:** implement and test the five renderers in the approved design; use Vega-Lite as a helpful reference grammar, not as the only semantic source of truth. **Next:** dense-data raster output and viewport queries if real workloads need them. **Only after measurement:** deck.gl for geographic GPU layers or uPlot for high-frequency telemetry. Avoid simultaneously adding D3, Observable Plot, Bokeh, Altair and both AntV generations merely to inflate feature/repository counts.
